# AllInOne Agent

AllInOne 是默认模式：一个 Agent 对用户负责，在同一上下文中完成必要的需求、实现、测试和环境步骤，
不创建子 Agent。

## 1. 适用范围

- 目标明确，验收标准容易确认；
- 工作集中在一个领域或一条顺序链路；
- 风险和外部影响可控；
- 没有必须独立执行的 QA、OPS 或并行研究；
- 单 Agent 可以在合理上下文和时间内完成并验证。

不能只按文件数量判断复杂度。一次机械重命名可能涉及很多文件但仍适合 AllInOne；一个涉及生产数据
迁移的小改动也可能需要 Agent Teams。

## 2. 顺序工作法

AllInOne 根据任务需要依次切换职责，但始终是同一个 Agent：

1. PMO：确认目标、授权范围和交付物；
2. PM：消除需求歧义，写出范围、非目标和验收标准；
3. RD：完成技术分析、Coding、调试和单元测试；
4. QA：执行自检和回归，保存证据；
5. OPS：仅在环境进入范围时验证构建、CI 或部署；
6. PMO：汇总结果、限制、Git 状态和下一步。

自检必须写成“本 Agent 验证通过”，不能写成“独立 QA 通过”。高风险结论若需要独立复核，应建议
Agent Teams，并先向用户申请。

## 3. 升级为 Agent Teams

执行中出现新的独立工作流、跨角色冲突、上下文显著膨胀、高影响外部操作或独立验收要求时，停止
扩张当前模式，按 [team-protocol.md](team-protocol.md) 提交启动提案。未获确认前继续做不依赖组队的
安全工作，不得预先创建子 Agent。

## 4. 模型使用

复杂 Coding 可使用 GPT-5.6 Sol `high` 一类的前沿 Coding 模型；长需求综合可使用 Fable 5 一类的
长任务模型；审查和谨慎操作可使用 Opus 5 一类的稳健模型。实际只有一个模型可用时，仍按上述顺序
分阶段工作，并通过外部测试与证据弥补缺少模型多样性的问题。

模型选择不改变权限，不能因为模型具备工具或长任务能力就自行 push、merge、部署或扩大需求。
