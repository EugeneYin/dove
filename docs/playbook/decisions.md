# 技术决策

记录选型理由与被否决的方案。改动前先看这里，多数「为什么不那样做」已经有答案。

## 网页而非原生 Android

最初的方案是 Kotlin + Compose 原生应用。改用网页的决定性理由是：**原生方案里
最难的那部分在网页上不存在**。

Android 自带的 `PdfRenderer` 只输出位图，没有文本层，取词得走 Pdfium 的 JNI
接口拿字符级 bbox，再自己做命中和词边界扩展。而 PDF.js 直接给出 DOM 文本层，
取词变成浏览器原生能力。

| 方案 | 渲染 | 文字坐标 | 结论 |
|---|---|---|---|
| Android `PdfRenderer` | ✅ | ❌ | 排除 |
| Pdfium (PdfiumAndroid) | ✅ | ✅ 需 JNI | 原生方案里唯一可行的 |
| MuPDF | ✅ | ✅ | AGPL，闭源发布需付费授权 |
| **PDF.js（网页）** | ✅ | ✅ 现成 DOM | **采用** |

附带收益：零安装门槛、一套代码覆盖 iPad/iPhone/Mac/Android，开发环境无需
Android SDK。代价是打开 PDF 的入口不如原生顺手（无法从文件管理器直接关联打开）。

## 不使用前端框架

应用主体是一块 canvas 加一个弹窗，状态量屈指可数。React 的收益抵不过它的
构建复杂度与体积。Vanilla TS + Vite 至今没有出现「早知道用框架就好了」的时刻。

## 离线词典而非在线 API

在线词典（有道 / DeepL / Free Dictionary）释义更丰富，但要联网、要 API Key、
有延迟和限流。查词是阅读中每分钟发生数次的高频动作，延迟直接破坏体验。

选择离线的代价是首次要下载 3.7MB，以及生僻词和部分英式拼写（如 `memorisation`）
查不到。实测阅读场景覆盖率足够。

## 词典裁剪到 5.7 万词

不是拍脑袋定的阈值。分析 ECDICT 全量 77 万词条时发现，**带词频排名的词天然止于
约 5.7 万**（`rank ≤ 50000` 与 `rank ≤ 80000` 结果完全相同），说明这个集合本身
就是语料库认定的「实际在用的英语词汇」。再并上柯林斯/牛津核心词与考试标签词。

## 语言包用 fast 而非标准版

`tessdata_fast` 1.9MB，标准版约 11MB。实测扫描书正文识别置信度 95 以上，
6 倍体积换不来相应的精度提升。

## 词典预压缩 + 客户端解压

服务器是否对 `.json` 启用 gzip 不可控，实测 Vite dev 就不压缩，裸传 9.9MB。
改为构建期生成 `.gz`，客户端按 gzip 魔数判断是否需要自己解压——两种情况都能
正确处理，不依赖部署环境。

## OCR 合成文本层，而非另建取词逻辑

扫描件本可以单独实现一套「按 OCR 坐标做命中测试」的逻辑，但那会产生两套需要
分别维护、分别测试、分别修 bug 的取词代码。

改为把 OCR 结果摆成与 PDF.js 相同结构的透明文本层后，`word.ts` 一行未改就同时
支持了两种 PDF。跨行连字符、所有格剥离、词形还原这些能力自动惠及扫描件。

## 自托管全部运行时资源

Tesseract.js 默认从 CDN 拉取核心与语言包。改为自托管的理由：断网可用是产品约束，
且 CDN 在国内不稳定。代价是 `dist/` 会包含三个 OCR 核心变体、体积较大，但运行时只下载其中一个
核心变体。具体体积由当前依赖和构建产物决定，不在决策文档中固定数值。

## E2E 分层使用 CDP 与 Playwright

原有交互回归由 `scripts/e2e.mjs` 使用 Chrome DevTools Protocol 驱动本机 Chrome；这部分建立时
可以直接使用 Node WebSocket，无须额外测试框架。完整 PWA 离线基线、设备模拟和 BrowserStack
真机链路则使用 Playwright，以获得浏览器进程控制、多项目配置、报告、Trace 和 CI 集成。

两层互相补充：CDP 脚本保留快速交互回归，Playwright 承担需要严格生命周期和可回溯证据的场景。
早期 CDP 回归第一次运行就抓到了词典因 gzip 双重解压而完全加载不了的问题——那是单元测试和
类型检查都覆盖不到的。

## 手写 Service Worker

没有用 `vite-plugin-pwa` / Workbox。需求就三件事：预缓存一份清单、cache-first、
拦一个分享 POST。采用手写 Service Worker 和小型构建插件，全部逻辑都看得见；具体行数不作为
架构约束。

Workbox 会带来一层运行时抽象和几百 KB 的构建依赖，而它擅长的那些场景——多种缓存策略
共存、按路由配过期、后台同步——这里一个都用不上。分层预缓存和「只缓存一个 OCR 核心变体」
反倒是它的默认清单生成器不方便表达的。

代价是更新逻辑得自己写对（`skipWaiting` 时机、旧缓存清理），这些都写进了上面的注释和
[pitfalls.md](pitfalls.md)。

## sw.js 是 JS 而非 TS

项目其余部分都是 TypeScript。Vite 8 换用 rolldown 之后 esbuild 不再随包安装，
而 TypeScript 7 是 Go 重写版，不再提供 `transpileModule` 之类的 JS API——想把
`sw.ts` 转成 JS，要么新增 esbuild 依赖，要么在构建插件里 spawn 一个编译器。

为一个 6KB、零 import 的文件做这些不划算。改用 JSDoc 标注类型 + `checkJs`，
类型检查一分不少（`pnpm run typecheck` 同时跑主配置与 `tsconfig.sw.json`），
构建时原样输出，只在顶部拼上注入的常量。

## 预缓存分成 SHELL 与 EXTRAS 两批

最初想把全部资源都放进 `install`。问题是 `install` 失败则 Service Worker 装不上，
一点离线能力都没有；而移动网络下下载 14.5MB 中断一次是常事，等于永远装不上。

改为外壳（1.8MB）阻塞、其余（12.7MB）由页面触发且逐文件跳过已缓存的。弱网下最坏情况
是分几次开应用才补齐，而不是全有或全无。

反过来也考虑过全部按需缓存（用到才存），但那样「第一次遇到扫描件时恰好没网」就是死路，
而扫描件可用是 README 里的不妥协约束。

## Service Worker 自己做 SIMD 探测

`tesseract.js` 的三个核心变体各约 4MB，运行时只用一个。让页面探测再告诉 SW 要多一轮
消息往返，而 SW 本身就是 worker 环境，`WebAssembly.validate` 直接可用，于是把
`wasm-feature-detect` 的两段探测字节内联进去，与 `tesseract.js` 内部保持一致。

代价是产生了一处必须跟着 `tesseract.js` 升级而核对的耦合，已在代码与文档里标注。
备选方案是三个全缓存，多占 8MB——对一个主打离线的应用来说，那 8MB 是纯浪费。

## 最近文档存 IndexedDB，但不做云同步

「不做阅读进度云同步」的约束没变。但装成主屏应用之后，点开是个空页面、每次都要回文件
管理器里翻同一本书，是明显的倒退；离线时文件选择器能否取到云盘文件本身也没保证。

存在本地既不违反那条约束，也让「随时打开接着读」成立。

## 保留 polyfill 而不要求用户升级系统

iPadOS 18.4 以下缺 `ReadableStream` 异步迭代。可以要求用户升级，但旧 iPad 往往
升不上去，而这类设备恰恰是阅读的主力。polyfill 只有 48 行，对新设备无害。
