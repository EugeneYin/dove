# 技术决策

记录选型理由与被否决的方案。改动前先看这里，多数「为什么不那样做」已经有答案。

## 网页而非原生 Android

最初的方案是 Kotlin + Compose 原生应用。改用网页的决定性理由是：**原生方案里
最难的那部分在网页上不存在**。

Android 自带的 `PdfRenderer` 只输出位图，没有文本层，取词得走 Pdfium 的 JNI
接口拿字符级 bbox，再自己做命中和词边界扩展。而 PDF.js 直接给出 DOM 文本层，
取词变成浏览器原生能力。

| 方案 | 渲染 | 文字坐标 | 结论 |
|---|---|---|---|
| Android `PdfRenderer` | ✅ | ❌ | 排除 |
| Pdfium (PdfiumAndroid) | ✅ | ✅ 需 JNI | 原生方案里唯一可行的 |
| MuPDF | ✅ | ✅ | AGPL，闭源发布需付费授权 |
| **PDF.js（网页）** | ✅ | ✅ 现成 DOM | **采用** |

附带收益：零安装门槛、一套代码覆盖 iPad/iPhone/Mac/Android，开发环境无需
Android SDK。代价是打开 PDF 的入口不如原生顺手（无法从文件管理器直接关联打开）。

## 不使用前端框架

应用主体是一块 canvas 加一个弹窗，状态量屈指可数。React 的收益抵不过它的
构建复杂度与体积。Vanilla TS + Vite 至今没有出现「早知道用框架就好了」的时刻。

## 离线词典而非在线 API

在线词典（有道 / DeepL / Free Dictionary）释义更丰富，但要联网、要 API Key、
有延迟和限流。查词是阅读中每分钟发生数次的高频动作，延迟直接破坏体验。

选择离线的代价是首次要下载 3.7MB，以及生僻词和部分英式拼写（如 `memorisation`）
查不到。实测阅读场景覆盖率足够。

## 词典裁剪到 5.7 万词

不是拍脑袋定的阈值。分析 ECDICT 全量 77 万词条时发现，**带词频排名的词天然止于
约 5.7 万**（`rank ≤ 50000` 与 `rank ≤ 80000` 结果完全相同），说明这个集合本身
就是语料库认定的「实际在用的英语词汇」。再并上柯林斯/牛津核心词与考试标签词。

## 语言包用 fast 而非标准版

`tessdata_fast` 1.9MB，标准版约 11MB。实测扫描书正文识别置信度 95 以上，
6 倍体积换不来相应的精度提升。

## 词典预压缩 + 客户端解压

服务器是否对 `.json` 启用 gzip 不可控，实测 Vite dev 就不压缩，裸传 9.9MB。
改为构建期生成 `.gz`，客户端按 gzip 魔数判断是否需要自己解压——两种情况都能
正确处理，不依赖部署环境。

## OCR 合成文本层，而非另建取词逻辑

扫描件本可以单独实现一套「按 OCR 坐标做命中测试」的逻辑，但那会产生两套需要
分别维护、分别测试、分别修 bug 的取词代码。

改为把 OCR 结果摆成与 PDF.js 相同结构的透明文本层后，`word.ts` 一行未改就同时
支持了两种 PDF。跨行连字符、所有格剥离、词形还原这些能力自动惠及扫描件。

## 自托管全部运行时资源

Tesseract.js 默认从 CDN 拉取核心与语言包。改为自托管的理由：断网可用是产品约束，
且 CDN 在国内不稳定。代价是 `dist/` 体积较大（13MB），但运行时只下载其中一个
核心变体。

## e2e 用 CDP 而非 Playwright

Node 24 自带 WebSocket，直接用 Chrome DevTools Protocol 驱动本机 Chrome 即可，
零新增依赖，也不需要下载额外的浏览器二进制。

这个选择很快证明了价值：第一次运行就抓到了词典因 gzip 双重解压而完全加载不了的
bug——那是单元测试和类型检查都覆盖不到的问题。

## 保留 polyfill 而不要求用户升级系统

iPadOS 18.4 以下缺 `ReadableStream` 异步迭代。可以要求用户升级，但旧 iPad 往往
升不上去，而这类设备恰恰是阅读的主力。polyfill 只有 48 行，对新设备无害。
